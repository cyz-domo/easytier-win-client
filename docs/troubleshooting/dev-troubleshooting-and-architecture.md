## 1. 多实例端口冲突与自动故障规避

### 问题现象
在客户端中创建并启动多个组网实例时，第二个实例启动失败并立即退出（Exit code: 1），标准错误输出显示：
`os error 10048: 通常每个套接字地址(协议/网络地址/端口)只允许使用一次。`

### 根因分析
1. **默认监听端口冲突**：EasyTier 默认 listener 为 `tcp://0.0.0.0:11010`、`udp://0.0.0.0:11010`、`wg://0.0.0.0:11011`。若实例未显式修改监听端口，第二个实例会试图绑定已被第一个实例占用的物理端口；
2. **虚拟网卡（TUN 设备）重名冲突**：若虚拟网卡名称均保留默认或为空，Wintun 驱动会由于适配器设备名冲突抛出 `Failed to create adapter`。

### 解决方案
- **动态监听端口自动适配**：在启动实例前，检查系统正在运行的其它实例已绑定的端口。若发现默认端口冲突，自动将当前实例的监听端口降级为动态端口（如 `tcp://0.0.0.0:0`），由系统动态分配可用端口；
- **独立 TUN 适配器命名**：若用户未指定虚拟网卡名，自动根据实例 UUID 生成唯一的 `et_<hash>` 设备名（如 `et_c59754`），避免多实例互相抢占同一个 Wintun 网卡。

## 2. 跨平台 RPC 远程配置与白名单管理

### 问题现象
客户端无法直接发现或连接 macOS 版本（`easytier-macos`）启动的 EasyTier 节点；且进行远程配置修改时存在安全顾虑。

### 根因分析
1. **默认绑定限制**：`easytier-core` 默认只在环回接口（`127.0.0.1:15888`）监听 RPC 管理端口，跨物理机或局域网无法直连；
2. **macOS/Linux/Windows 跨平台差异**：macOS 版本默认 RPC 端口通常为 `15888`（或动态分配），且只有当命令行显式指定 `--rpc-portal 0.0.0.0:15888` 时才对外暴露。

### 解决方案
- **远程管理开关与白名单约束**：
  在客户端配置中增加「允许远程管理」开关。开启后，RPC 监听地址自动变更为 `0.0.0.0:<port>`，并**强制要求填写 RPC 白名单 CIDR**（默认自动附加虚拟网段与 `127.0.0.1/32`），防止管理端口向公网或物理不可信局域网暴露；
- **智能候选端口轮询探测**：
  连接远程节点时，支持指定目标 IP 并在常用候选端口（如 `15888`, `15889`, `15890`）中执行快速 TCP 握手探测，自动匹配可用 RPC 端口。

## 3. 主机名与子网代理对端 TOML 双向同步

### 问题现象
通过 RPC 远程修改对端的主机名（hostname）或子网代理（proxy_cidrs）后，对端内存生效，但其本地的配置文件（TOML）和客户端表单未更新，重启后配置丢失。

### 解决方案
- **两阶段提交与热补丁同步**：
  前端修改主机名或子网代理时，不仅调用 `patch_network_config` 实时更新运行中核心，同时触发对端配置的写入回调；
- **表单状态深度响应**：
  前端监听 RPC 返回的最新 Snapshot，当发现远程节点返回了更新后的主机名和代理网段时，无缝同步至当前 React 表单与 LocalStorage 缓存。

## 4. 内核多版本切换、完整性校验与备份回滚

### 问题现象
早期内核切换仅支持在线下载，下载后无法复用历史版本；且如果新下载的核心出现兼容性问题（如特定 Windows 版本崩溃），缺少安全回滚手段。

### 解决方案
- **本地多版本缓存复用**：
  将已下载的内核按版本归档存储在本地缓存目录（如 `core/versions/v2.6.4/`）。再次切换到该版本时，先进行 SHA256 完整性校验，校验通过直接就地切换，无需重新联网下载；
- **原子级备份与回滚**：
  在替换 `easytier-core.exe` 之前，将当前正常工作的核心备份为 `core/easytier-core.exe.bak`。启动新核心后执行 `wait_for_exit` 探测，若新核心在 1.5 秒内崩溃退出，客户端自动将备份核心回滚还原，保障网络服务不中断。

## 5. Windows 服务在虚拟机/精简版环境的适配与自愈

### 问题现象
在虚拟机（如精简版 Windows 10/11）中点击“安装后台服务”时，出现安装失败、服务无法启动或 IPC 管道无响应。

### 解决方案
- **SCM 服务控制管理器权限保障**：
  服务注册与管理调用底层 Win32 API（`CreateServiceW`, `StartServiceW`），并在非管理员环境下提供一键“以管理员身份重启客户端”能力；
- **心跳探测与自动修复（Self-Healing）**：
  客户端每 20 秒对服务状态执行轻量检测。若发现服务意外停止，自动执行 `repair_service` 指令重新拉起，恢复网络实例。

## 6. WebView2 高 CPU (75%) 与 GPU 3D 渲染死循环治理

### 问题现象
1. GUI 打开运行时，CPU 占用高达 ~75.4%，虚拟机明显发热卡顿；
2. 关闭窗口最小化至系统托盘后，任务管理器中 `Microsoft Edge WebView2` 仍消耗 **8.8% CPU** 与 **11.4% GPU 3D**。

### 根因深剖
1. **重度 CSS 高斯模糊光栅化**：
   页面根节点存在两个 580px 的 `@keyframes liquid-drift` 旋转动画，叠加了 `filter: blur(95px)`。在缺乏独立硬件 GPU 加速的虚拟机环境下，Chromium 只能靠 CPU 以 60 FPS 软件模拟超大半斤的高斯模糊，空转吃满 60% CPU；
2. **Chromium 遮挡检测被显式屏蔽**：
   在 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` 启动参数中，错误地包含了 `--disable-features=CalculateNativeWinOcclusion`、`--disable-renderer-backgrounding` 和 `--disable-background-timer-throttling`。
   - 这导致 Chromium 即使在原生 HWND 被 `SW_HIDE` 隐藏后，**依然坚信窗口位于屏幕最顶层可见**，永不停止 GPU 交换链；
3. **无限 CSS 状态呼吸灯**：
   DOM 中在线节点的 `.dot.on` 带有 `animation: pulse-glow 2.4s infinite`。配合上述屏蔽遮挡检测，GPU 进程（`--type=gpu-process`）在后台永不停歇地进行 3D 帧提交，单进程独占 9.38% CPU。

### 彻底优化方案
- **移除重度光栅化滤镜**：删除 `filter: blur(95px)` 与旋转动画，改用零计算开销的静态柔和径向渐变；
- **去除所有无限关键帧动画**：将 `.dot.on` 状态点改为纯静态微光质感（0 FPS，零重绘）；
- **恢复 Chromium 原生遮挡检测与后台降频**：彻底剔除阻止休眠的 3 个启动参数，让 Chromium 随原生窗口隐藏自动挂起 GPU 渲染交换链；
- **全页面后台动画冷冻**：当窗口处于托盘或最小化时，根节点注入 `[data-window-hidden="true"]`，强行冻结页面所有 CSS 动画与 Transition，同时挂起所有高频轮询定时器。**后台 CPU 占用降至 0.0%**。

## 7. Windows Job Object 进程树约束杜绝孤儿进程

### 问题现象
关闭 GUI 或直接结束 `easytier-win-client.exe` 后，残留两个 `msedgewebview2.exe` 进程在后台继续死循环消耗 CPU。

### 根因分析
WebView2 为多进程架构（Browser、Renderer、GPU、Utility 等）。当父进程因崩溃或非正常路径终止时，若未纳入操作系统的 Job Object 统一监管，子进程会脱离成为孤儿进程常驻系统。

### 解决方案
在 Rust 客户端启动的最早阶段（`lib.rs::job_object::init_global_job`），通过 Win32 API：
1. `CreateJobObjectW` 创建系统作业对象；
2. `SetInformationJobObject` 配置 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`；
3. `AssignProcessToJobObject` 将当前进程与作业绑定。
**内核级保证**：无论父进程因何种原因退出，Windows 操作系统内核会在微秒级原子性连带销毁其所有子孙进程，彻底杜绝孤儿进程泄漏。

## 8. 双轨自启动体系架构（桌面自启与服务自启）

### 需求与场景
用户需要开机后网络自动就绪，但在不同环境（普通桌面用户 vs 服务器/虚拟机无人值守）下需求不同。

### 双轨实现设计
1. **桌面自启（GUI 随 Windows 启动）**：
   - 写入当前用户注册表：`HKCU\Software\Microsoft\Windows\CurrentVersion\Run\EasyTierWinClient`；
   - **免提权优势**：写入 `HKCU` 无需弹出 Windows UAC 提权窗口，绿色便携版和安装版完全通用；
   - **静默托盘参数**：支持附加 `--minimized` 参数。开机进入桌面后静默启动并常驻右下角托盘，不弹出窗口打扰用户；
   - **启动时自连**：客户端初始化挂载时，自动遍历勾选了“自动启动”的网络实例并调用 `start_instance`，实现**开机进桌面 -> 程序启动 -> 网络自动连接**。
2. **系统服务自启（无需登录桌面）**：
   - 安装后台 Windows 服务（`EasyTierService`），启动类型设为 `SERVICE_AUTO_START`；
   - 电脑通电开机时，服务在 Windows 登录界面前即自动运行，并直接拉起所有勾选了“自动启动”的实例，适合服务器、NAS、虚拟机等无人值守场景。

## 9. 流量统计生命周期与“会话累计”机制

### 问题现象
“累计收发（重连不丢失）”在客户端关闭重启后，旧历史流量依旧残留，无法重置。

### 机制校正与重构
- **概念澄清**：
  “重连不丢失”的真实语义是**单次网络连接会话期间**，对端节点发生短暂网络抖动、链路切换或 P2P 重协商时，由于底层核心计数器清零，前端累加池保护累计数据不归零；
- **生命周期约束为会话级（Session-Scoped）**：
  1. 移除持久化存储至 `localStorage` 的机制，数据纯保存在应用运行期内存中；
  2. 当用户**重新启动连接网络**或**重启客户端程序**时，自动重置该实例的流量累计为 0；
  3. 界面文案优化为：`本次累计（重连不丢失）`，并保留手动“清零”按钮供随时重置。

## 10. 注册表句柄 RAII 守卫与便携版路径失效自愈机制

### 隐患排查
1. **`HKEY` 句柄早期返回泄露**：原注册表操作在成功调用 `RegCreateKeyExW` 打开句柄后，若获取可执行文件路径（`current_exe()`）失败，通过 `?` 提前返回，导致打开的句柄未调用 `RegCloseKey` 而永久泄露；
2. **`--minimized` 假阳性匹配**：检测注册表中的启动参数时，若运行路径本身带有 `--minimized` 目录名，直接 `val_str.contains` 会引发误判；
3. **便携版路径移动失效**：便携版用户常在移动文件夹后发现开机自启不再生效，但界面依然显示“已开启”，缺乏感知。

### 解决方案
- **RAII `RegKeyGuard` 守卫**：实现 Win32 `HKEY` 的 Drop 特征，任何错误分支跳出均保证句柄在栈展开时自动闭合；
- **参数截取精确匹配**：解析注册表命令行，先闭合可执行文件路径的双引号，仅对后面的命令行参数尾部进行切分与匹配；
- **路径过期检测与一键修复**：比对注册表中的可执行文件路径与当前进程 `current_exe()`。若路径不一致，标记 `path_mismatch` 并在界面提示失效告警，提供「更新为当前路径并重新激活」一键修复操作；
- **原生宽字符无损传递**：直接采用 `std::os::windows::ffi::OsStrExt::encode_wide` 编码注册表命令行，规避 UTF-8 有损转换损坏特殊字符路径。

## 11. 双重轮询消除与前端巨石组件模块化重构

### 性能瓶颈
原应用中 1 秒流量采样器（用于绘制近 30 秒流量折线图）与 5 秒节点/路由轮询同时活跃，导致单位时间内向同一个 RPC 端点发起过多请求，频繁派生后台 CLI 进程，空闲负载偏高。同时 `App.tsx` 超过 2150 行，41 个状态耦合导致单点数据变动触发全树重新渲染。

### 架构解耦与优化
1. **轮询管道合并**：
   - 移除独立的 1 秒流量轮询，收归统一轮询控制器；
   - 处于 Status 标签页时采用自适应 1-2 秒单轮询，在同一个 RPC 数据包中同步完成拓扑快照更新、会话累计流量累加与瞬时速率计算；
   - 消除对 `sessionStorage` 高频序列化写入开销，数据纯内存维护。
2. **组件与 Hooks 分层**：
   - 抽取 `useInstances`、`useService`、`useTraffic`、`useKernelUpdate` 四大核心业务 Hook；
   - 拆解 `StatusTab`、`PeersTab`、`RoutesTab`、`ConfigTab`、`LogsTab`、`SettingsTab` 六大标签页组件；
   - 主入口 `App.tsx` 从 2152 行缩减至约 740 行，渲染风暴彻底隔绝，代码可维护性大幅提升。
